## Entities

### Mission

> `source/server/battle_content.py`

Represents a playable quest, stage, or story event record configured in game content.

**Properties:**

| Name | Type | Description |
|------|------|-------------|
| id | string | Unique identifier for the mission |
| carrier | object | Envelope payload holding mission parameters and battle bundle responses |
| is_menu_resource | boolean | Flag indicating if the record is a banner/UI resource rather than an executable battle |

**Relationships:**

- has-many MissionPhase (A mission contains one or more phase stages or story scenes)
- generates BattleBundle (A mission resolves and compiles into a battle bundle response)

### MissionPhase

> `source/server/battle_content.py`

Represents an individual wave, combat stage, or non-combat narrative scene within a mission.

**Properties:**

| Name | Type | Description |
|------|------|-------------|
| id | string | Identifier for the mission phase |
| tokens | array | Token set conforming to the MissionPhaseMstResponse wire format |
| is_combat | boolean | Differentiates combat waves from story scene phases |

**Relationships:**

- belongs to Mission (Phase belongs to a specific mission definition)
- spawns MonsterPart (Combat phases reference monster parts in active encounter groups)

### BattleBundle

> `source/server/battle_content.py`

Represents the compiled wire response served to the client for battle execution, exploration, or
story events.

**Properties:**

| Name | Type | Description |
|------|------|-------------|
| reply_id | string | Response packet identifier (defaults to BATTLE_BUNDLE_REPLY_ID 'jnw49dUq') |
| carrier | object | Base response carrier holding encounter groups and phase data |
| encounter_groups | array | Encounter group definitions for combat waves |
| drop_rows | array | Reward and item drop definitions for the encounter |

**Relationships:**

- fulfills Mission (Compiled response payload derived from a mission definition)
- contains MonsterPart (Encapsulates monster parts, break gauges, and extended status data)
- contains Skill (Encapsulates recovered battle skill sets served in the payload)

## Requirements

### Requirement: MissionValidation

The system SHALL validate Mission according to these rules:
- Banner-only mission records are UI resources and must not be treated as executable battles
- Zero-wave story missions must retain original non-combat phases and dispatch bundles with empty encounter groups

#### Scenario: IdentifyUIResourceRecords
- **GIVEN** A banner-only mission record
- **WHEN** is_menu_resource_row is evaluated
- **THEN** Returns true to exclude the row from battle resolution

#### Scenario: GenerateStoryMissionBundle
- **GIVEN** A zero-wave story mission and carrier dictionary
- **WHEN** story_mission_bundle is invoked
- **THEN** Produces a battle bundle containing non-combat scene phases and no combat encounters

### Requirement: MissionPhaseValidation

The system SHALL validate MissionPhase according to these rules:
- Only tokens defined in PHASE_TOKENS (MissionPhaseMstResponse) may be dispatched on the wire

#### Scenario: ExtractStoryPhases
- **GIVEN** A story mission identifier
- **WHEN** story_mission_phases is called
- **THEN** Non-combat phases entering story scenes are retained

### Requirement: BattleBundleValidation

The system SHALL validate BattleBundle according to these rules:
- BREAK_TAG ('BJ6A0KTt') zeroes the pool and must never be emitted
- Weapon-resist parameters (RHe5r72C/EwZ40mt3) must remain unsent when source data is absent
- Story event bundles must emit carrier payloads with all encounter groups empty

#### Scenario: BuildExplorationFieldMissionBundle
- **GIVEN** A field exploration mission
- **WHEN** field_mission_bundle is compiled
- **THEN** Returns bundle containing enemy encounters without opening combat phases

#### Scenario: BuildIosPinnedFieldPlan
- **GIVEN** An initialized iOS campaign with field encounters enabled and a pinned plan
- **WHEN** field_mission_bundle is compiled
- **THEN** Finite encounters follow the pinned zone budgets and native occurrence indexes
- **AND** Script-bound bosses, explicit group bindings, and native monster/skill dependencies remain present
- **AND** Derivation writes no disk cache and grants no hypothetical loot
- **AND** Disabled or unplanned fields use the canonical field path; legacy behavior is preserved

#### Scenario: AssembleBattlePayloadWithAtomicCacheWrite
- **GIVEN** A battle mission request and cache destination
- **WHEN** assemble is executed
- **THEN** The derived wire bundle is written to disk atomically and returned

### Requirement: MonsterPartValidation

The system SHALL validate MonsterPart according to these rules:
- Missing monster part fields must fallback to PARTS_DEFAULTS ('2U3Zbxpy': '0', '0ePkR9nZ': '0')
- Dispatched part parameters must only use tokens defined in PARTS_TOKENS

#### Scenario: DeriveMonsterPartAttributes
- **GIVEN** Encounter part records with missing defaults
- **WHEN** derive_mission processes part rows
- **THEN** Applies PARTS_DEFAULTS and compiles break and external status rows

### Requirement: SkillValidation

The system SHALL validate Skill according to these rules:
- Skill ID must be unique and correspond to a defined skill action

#### Scenario: ServeSkillSetInBattlePayload
- **GIVEN** A monster encounter configured with skill IDs '222979' and '222980'
- **WHEN** Battle payload generation executes
- **THEN** Skill rows for 'Flying Attack' and 'Flame Breath' are served in the active battle payload

### Requirement: UnitValidation

The system SHALL validate Unit according to these rules:
- Unit must possess recognized form IDs matching supported forms
- Unit must belong to specified rule categories ('Another World' or 'FFBE S4') to enter restricted event stages

#### Scenario: VerifyEventEntryRestrictions
- **GIVEN** A unit assigned to the 'Another World' or 'FFBE S4' category
- **WHEN** The unit is selected for an event stage team
- **THEN** The unit passes the entry category check and enters the battle

### Requirement: FieldTreasureValidation

### Requirement: DisplayResolutionValidation

The system SHALL validate DisplayResolution according to these rules:
- width, height, frameWidth, and frameHeight must all be positive finite numbers
- Fixed-width scaling (policy 4) applies when frame aspect ratio is taller than or equal to canvas aspect ratio (frameHeight / frameWidth >= height / width)
- Fixed-height scaling (policy 3) applies when frame aspect ratio is wider than canvas aspect ratio

#### Scenario: SelectFixedWidthScalingForTallDisplayFrames
- **GIVEN** A display frame where frameHeight / frameWidth >= height / width
- **WHEN** chooseResolution is called with valid positive dimensions
- **THEN** Returns resolution configuration with policy 4, original canvas width, and scaled height

#### Scenario: SelectFixedHeightScalingForWideDisplayFrames
- **GIVEN** A display frame where frameHeight / frameWidth < height / width
- **WHEN** chooseResolution is called with valid positive dimensions
- **THEN** Returns resolution configuration with policy 3, scaled width, and original canvas height

#### Scenario: HandleInvalidOrNonPositiveFrameDimensions
<!-- openlore-test: tags=regression (auto) -->
- **GIVEN** Input dimensions containing non-finite or non-positive values
- **WHEN** chooseResolution is called
- **THEN** Returns null

### Requirement: LayoutBoxValidation

The system SHALL validate LayoutBox according to these rules:
- Tall list detection requires the box not to start with 'home_' or match dialog/popup/tooltip patterns
- Tall list detection requires box height to be at least 25% of reference height and vertical span between 75% and 84% of reference height
- Footer background elements stretch horizontally by the delta between canvas width and reference width

#### Scenario: AnchorFooterLayoutElement
- **GIVEN** A layout box with a 'footer_' name prefix
- **WHEN** anchorLayout is called with reference and canvas specifications
- **THEN** Element x is shifted by canvas horizontal delta and y is shifted by canvas vertical delta plus
footer gap

#### Scenario: StretchVerticalListLayoutBox
- **GIVEN** A layout box recognized as a tall list container
- **WHEN** anchorLayout is called with canvas delta
- **THEN** Element height is expanded by canvas vertical delta

### Requirement: CampaignBannerValidation

The system SHALL validate CampaignBanner according to these rules:
- Only layout boxes positioned at or below banner bottom edge (original.y >= banner.y + banner.height - 1) are shifted
- Footer and bottom layouts are exempt from banner collapse adjustments

#### Scenario: CollapseBannerAndShiftFollowingLayoutElements
- **GIVEN** A layout box positioned below an active banner
- **WHEN** collapseCampaignBanner is called
- **THEN** The layout box y coordinate is reduced by banner height

#### Scenario: CollapseBannerAndExpandTallListContainer
- **GIVEN** A tall list layout box positioned below an active banner
- **WHEN** collapseCampaignBanner is called
- **THEN** The layout box y coordinate is reduced by banner height and its height is increased by banner height

### Requirement: MapViewportValidation

The system SHALL validate MapViewport according to these rules:
- Map scroll coordinates x and y are constrained within minimum and maximum bounds determined by column and row tile extents and viewport dimensions

#### Scenario: ClampOutOfBoundsMapScrollCoordinates
- **GIVEN** Scroll coordinates extending past valid grid boundaries
- **WHEN** clampMapScroll is called with map column/row counts and viewport dimensions
- **THEN** Returns coordinates clamped within maximum permissible scroll limits

### Requirement: MonsterValidation

The system SHALL validate Monster according to these rules:
- Monster parts must map to valid part IDs and group IDs
- Monster must possess at least one combat skill or phase configuration

#### Scenario: DeriveMissionEncounter
- **GIVEN** Mission parameters and enemy master data for Beast King Gnon
- **WHEN** derive_mission is invoked
- **THEN** Encounter records, break parts, phase rows, and drop tables are assembled into the battle encounter
catalogue

### Requirement: PlateManifestValidation

The system SHALL validate PlateManifest according to these rules:
- Manifest must be located at manifest.json within the payload directory
- Prefix guard hex strings must be parsed into 64-byte verification signatures

#### Scenario: LoadPlateManifest
- **GIVEN** A valid manifest.json exists in the payload directory
- **WHEN** Initialization routine reads and parses the manifest
- **THEN** Plate files are indexed by size and prefix guards are compiled into byte arrays

#### Scenario: ValidatePlatePrefixMatch
- **GIVEN** An incoming image buffer and configured prefix guards for its byte size
- **WHEN** matchesPlatePrefix is executed against the candidate data
- **THEN** Returns true if candidate data matches any 64-byte prefix guard or if no guards are configured

### Requirement: PlateAssetValidation

The system SHALL validate PlateAsset according to these rules:
- File descriptor must be opened and fully read from the payload directory
- Asset buffer length must match the key defined in the manifest

#### Scenario: SwapImageAssetOnInitialization
- **GIVEN** A plate replacement asset loaded in memory matching the requested image length and prefix guard
- **WHEN** initWithImageData hook is entered with target image data pointer and length
- **THEN** Native image data pointer argument is replaced with the plate asset buffer pointer

### Requirement: LimitBurstMasterValidation

The system SHALL validate LimitBurstMaster according to these rules:
- Asset requests must not already be in-flight before triggering background downloads
- Unavailable or invalid Limit Burst entries are rejected before network requests are initiated
